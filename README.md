# Учебный Raft

Java 25, Spring Boot 4, Gradle. Реализован первый этап: выборы лидера, heartbeat и статус узла.

Lombok генерирует SLF4J-логгеры (`@Slf4j`), простые конструкторы зависимостей
(`@RequiredArgsConstructor`) и выбранные геттеры (`@Getter`). `@Accessors(fluent = true)`
сохраняет имена методов вроде `snapshot()` и `leaderId()`. DTO остаются `record`;
переходы ролей и изменение состояния Raft задаются явными методами.
Lombok нужен только при компиляции и не включается в запускаемый JAR.

## Запуск

```sh
./gradlew test bootJar
java -jar build/libs/raft-0.0.1-SNAPSHOT.jar
```

При старте приложение читает общий внешний файл `config/cluster.yaml`. В нём хранятся
все участники кластера в виде карты `id → url`, включая текущую ноду:

```yaml
raft:
  nodes:
    node-1: http://node-1:8080
    node-2: http://node-2:8080
    node-3: http://node-3:8080
```

Spring связывает эту секцию с неизменяемой `Map<String, URI> nodes` в `ClusterProperties`.
Свой ID процесс получает через `RAFT_NODEID` или `--raft.node-id` (по умолчанию `node-1`).
Метод `peers()` исключает собственный ID; размер кластера и кворум считаются по всей карте.
Пустая карта, неизвестный собственный ID, некорректный URL или повторяющийся ключ YAML
останавливают запуск с ошибкой.

`application.yaml` подключает YAML через `spring.config.import`. Путь можно изменить
переменной `RAFT_CONFIG`; по умолчанию это `./config/cluster.yaml` относительно рабочего каталога.
Файл обязателен и читается до запуска event loop. Состав кластера статический:
изменения применяются при перезапуске, динамическое изменение членства не реализовано.

Для нескольких JVM на одной машине укажи в общем файле адреса `http://localhost:8081`,
`http://localhost:8082` и `http://localhost:8083`. Запуск второй ноды:

```sh
RAFT_CONFIG=/absolute/path/cluster.yaml RAFT_NODEID=node-2 \
  java -jar build/libs/raft-0.0.1-SNAPSHOT.jar --server.port=8082
```

URL — адрес для межузловой связи; порт HTTP-сервера задаётся отдельно через `SERVER_PORT`
или `--server.port`. Для одиночного запуска оставь в карте только собственную ноду.

## Запуск через Docker Compose

```sh
docker compose build node-1
docker compose up -d --no-build
docker compose logs -f
```

`Dockerfile` собирает приложение Gradle Wrapper на Java 25 и запускает JAR на
Java 25 JRE от пользователя `raft`. Предварительная сборка JAR на хосте не нужна.
Три узла используют общий образ `cringe-raft:local`. Для выборов нужен кворум из двух узлов.

Адреса всех нод задаются один раз в `config/cluster.yaml`. Compose монтирует этот файл
во все контейнеры только для чтения. Для каждого сервиса остаются `RAFT_NODEID` и
публикация порта; списки пиров в переменных окружения больше не нужны.

| Сервис   | Адрес для пиров      | API с хоста             |
|----------|----------------------|-------------------------|
| `node-1` | `http://node-1:8080` | `http://localhost:8081` |
| `node-2` | `http://node-2:8080` | `http://localhost:8082` |
| `node-3` | `http://node-3:8080` | `http://localhost:8083` |

Пиры обращаются друг к другу по именам сервисов, например `http://node-2:8080`:
Docker сам назначает IP и разрешает имена сервисов. Порт `8080` используется внутри сети,
а `ports` задаёт доступ с хоста. При необходимости URL пиров можно заменить
прямыми IP-адресами в `config/cluster.yaml`.

После изменения адресов в YAML перезапустите процессы:

```sh
docker compose restart
```

Добавление ключа в карту не запускает новый контейнер: для новой ноды также нужен
сервис Compose или отдельная JVM. Все участники должны читать одинаковую карту.

Проверка состояния и остановка лидера для проверки перевыборов:

```sh
curl localhost:8081/status
curl localhost:8082/status
curl localhost:8083/status
# Если лидером оказался node-1:
docker compose stop node-1
docker compose start node-1
```

`docker compose down` останавливает весь кластер. Терм и голос хранятся в памяти,
поэтому остановка всех контейнеров стирает состояние выборов.

## API

Swagger UI доступен на каждом узле: `http://localhost:8081/swagger-ui.html`
(также порты 8082 и 8083). OpenAPI JSON: `/v3/api-docs`, YAML: `/v3/api-docs.yaml`.

- `GET /status`: `nodeId`, `role`, `term`, `leaderId` (null до обнаружения лидера).
- `POST /raft/request-vote`: запрос голоса `{ "term": 1, "candidateId": "node-2" }`;
  ответ `{ "term": 1, "voteGranted": true }`.
- `POST /raft/append-entries`: heartbeat `{ "term": 1, "leaderId": "node-2" }`;
  ответ `{ "term": 1, "success": true }`.

```sh
curl localhost:8081/status
```

`AppendEntries` используется только для heartbeat. Поля лога в RPC, `/entries` и `/log`
удалены. Репликация записей, commit index и клиентские команды отсутствуют.
Запросы с отрицательным термом или пустым ID отклоняются с HTTP 400.
Ожидание входящего RPC ограничено `raft.rpc-timeout`; при таймауте возвращается HTTP 503.

## Устройство

`RaftNodeConfiguration` создаёт узел, `RaftRuntimeConfiguration` — очередь, event loop
и таймеры, `PeerClientConfiguration` — HTTP-клиент и виртуальные потоки транспорта.

Все события обрабатываются одним потоком `EventLoop`. `RaftNode.handle` выбирает
обработчик по классу события из неизменяемой карты в `RaftEventConfiguration`.
Для каждого события есть отдельный класс в `node.handler`. Обработчики вызывают
методы текущей роли: `FollowerState`, `CandidateState` или `LeaderState`.
Для нового события нужно добавить handler и регистрацию в конфигурационной карте;
тест проверяет покрытие всех типов sealed-интерфейса `RaftEvent`.

Фолловер сбрасывает election timer при heartbeat и выдаче голоса. Таймаут запускает
выборы с новым термом и голосом за себя. Кандидат учитывает только уникальные голоса
участников кластера из текущего терма. Лидер отключает election timer, сразу рассылает
heartbeat и продолжает рассылку периодически. Больший терм в любом RPC или ответе
переводит ноду в фолловера. У таймера есть эпоха для отбрасывания устаревших событий.

После обработки события, в том числе при исключении, публикуется неизменяемый
`NodeStatus` через volatile-поле `snapshot`. Контроллер `/status` читает этот снимок.
Контроллеры RPC ждут `reply.get()` на виртуальных HTTP-потоках. Сетевые запросы к пирам
также выполняются на виртуальных потоках и возвращают ответы через очередь событий.
Обработчики event loop не выполняют сетевые вызовы и не блокируются.

Параметры `raft.election-timeout-min`, `raft.election-timeout-max`,
`raft.heartbeat-interval`, `raft.rpc-timeout`, `raft.transport.connect-timeout` и
`raft.transport.read-timeout` задаются в YAML. Переходы ролей и голосование логируются
на INFO; ошибки транспорта — DEBUG, heartbeat — TRACE.

## Проверка отказа

1. По `/status` найдите лидера: остальные ноды должны указывать его `leaderId`.
2. Остановите лидера. Две оставшиеся ноды выберут нового с большим термом.
3. Запустите остановленную ноду с прежним ID и общим конфигом: она обнаружит лидера.

Автоматическая проверка на трёх реальных JVM:

```sh
./gradlew test bootJar
python3 scripts/cluster-smoke.py
```

Скрипт создаёт временный общий YAML с локальными адресами, проверяет выборы,
перевыборы после отказа и возврат остановленной ноды, затем завершает свои процессы.

## Границы реализации

Состав кластера статический. Для выборов необходимо большинство всех настроенных нод.
Потеря большинства сама по себе не заставляет действующего лидера отказаться от роли:
check-quorum не реализован.

Терм и голос хранятся только в памяти. Гарантии Raft при произвольных перезапусках
требуют сохранения этих данных на диск. Репликация лога (этап 2), key-value, CAS
и distributed lock (этапы 3–4) в этой версии не реализованы.
