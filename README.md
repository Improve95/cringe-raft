# Учебный Raft

Java 25, Spring Boot 4, Gradle. Реализованы выборы лидера и репликация лога (этапы 1 и 2).

## Запуск

```sh
./gradlew test bootJar
```

В трёх терминалах:

```sh
java -jar build/libs/raft-0.0.1-SNAPSHOT.jar --spring.profiles.active=node1
java -jar build/libs/raft-0.0.1-SNAPSHOT.jar --spring.profiles.active=node2
java -jar build/libs/raft-0.0.1-SNAPSHOT.jar --spring.profiles.active=node3
```

Порты — 8081, 8082, 8083. Без профиля запускается отдельный узел на 8081: он сам избирается лидером. Параметры и состав
кластера задаются в `src/main/resources/application.yaml`; каждый узел перечисляет всех остальных пиров, без себя.
Состав кластера статический.

## Запуск через Docker Compose

```sh
docker compose up --build -d
docker compose logs -f
```

`Dockerfile` собирает приложение Gradle Wrapper на Java 25 и запускает JAR на
Java 25 JRE от пользователя `raft`. Предварительная сборка JAR на хосте не нужна.
Compose собирает образ через сервис `node-1`; все три узла используют этот образ.

Все адреса и состав кластера для контейнеров задаются в `docker-compose.yaml`.
Spring получает id узла и список пиров через переменные окружения `RAFT_NODEID`,
`RAFT_PEERS_0_ID`, `RAFT_PEERS_0_URL` и аналогичные для следующего пира.
Профили `node1`/`node2`/`node3` для контейнеров не используются.

| Сервис   | IP внутри Docker | API с хоста             |
|----------|------------------|-------------------------|
| `node-1` | `172.28.0.11`    | `http://localhost:8081` |
| `node-2` | `172.28.0.12`    | `http://localhost:8082` |
| `node-3` | `172.28.0.13`    | `http://localhost:8083` |

Чтобы изменить IP, отредактируйте `services.<node>.networks.raft.ipv4_address`.
Адреса должны быть уникальными и входить в подсеть `networks.raft.ipam.config[].subnet`.
Пиры обращаются друг к другу по именам сервисов, например `http://node-2:8080`:
Docker сам разрешает имя в заданный IP. Порт `8080` используется внутри сети,
а `ports` задаёт доступ с хоста. При необходимости URL пиров можно заменить
прямыми IP-адресами в тех же переменных окружения.

После изменения адресов пересоздайте сеть и контейнеры:

```sh
docker compose down
docker compose up -d
```

Проверка состояния и остановка лидера для проверки перевыборов:

```sh
curl localhost:8081/status
curl localhost:8082/status
curl localhost:8083/status
# Если лидером оказался node-1:
docker compose stop node-1
docker compose start node-1
```

`docker compose down` останавливает весь кластер. Лог и терм хранятся в памяти,
поэтому остановка всех контейнеров стирает состояние кластера.

## API

```sh
curl localhost:8081/status
curl localhost:8081/log
# Отправлять на порт текущего лидера, указанный узлами в /status:
curl -X POST localhost:8081/entries -H 'Content-Type: application/json' -d '{"command":"hello"}'
```

- `GET /status`: `nodeId`, `role`, `term`, `leaderId` (null до обнаружения лидера).
- `GET /log`: неизменяемый снимок `entries` и `commitIndex`. Записи после `commitIndex` пока не подтверждены.
- `POST /entries`: строковая `command`; ответ `{ "index": 2, "term": 1 }` после фиксации большинством. Фолловер
  возвращает HTTP 409 и известный `leaderId`. Сетевую переадресацию выполняет клиент.
- `POST /raft/request-vote`, `POST /raft/append-entries`: межузловые RPC.

Индексы записей начинаются с 1; индекс 0 — пустой префикс с термом 0. После избрания лидер добавляет служебную запись с
`command: null`: большинство может фиксировать подсчётом реплик только записи текущего терма (§5.4.2). Такая запись
позволяет зафиксировать предыдущий префикс без ожидания клиентской команды. Клиентские команды не могут быть пустыми или
null.

RPC и ожидание фиксации ограничены `raft.rpc-timeout` (по умолчанию 1 секунда). HTTP 503 при таймауте **не означает**,
что запись отвергнута: она может зафиксироваться позднее. Повторная отправка создаст новую запись; дедупликация
клиентских запросов пока не реализована. Таймаут Spring MVC должен быть больше `raft.rpc-timeout`.

Создание `RestClient` и базового `HttpClient` вынесено в `PeerClientConfiguration`.
`RaftNodeConfiguration` создаёт узел и лог; `RaftRuntimeConfiguration` создаёт
очередь, event loop, таймеры и их планировщик. `RaftWebConfiguration` задаёт
таймаут Spring MVC больше таймаута RPC. Все эти зависимости собираются через
методы `@Bean`, без создания инфраструктуры внутри бизнес-классов.
Spring связывает `ClusterProperties` с секцией `raft`, а `PeerClientProperties` — с
`raft.transport`. Параметры можно переопределять в YAML, в том числе для отдельных
профилей:

```yaml
raft:
  rpc-timeout: 2s
  transport:
    connect-timeout: 500ms
    read-timeout: 3s
```

`connect-timeout` ограничивает установку исходящего соединения, `read-timeout` —
ожидание ответа пира. `rpc-timeout` ограничивает обработку входящего RPC и ожидание
клиентом фиксации записи. Значения длительностей должны быть положительными.

## Устройство

Внешние запросы, таймеры и ответы транспорта поступают в `EventQueue`. Единственный поток `EventLoop` меняет `RaftNode`,
`RaftLog` и текущий объект роли. Единственный switch в `RaftNode.handle` выбирает тип события; поведение ролей находится
в `FollowerState`, `CandidateState`, `LeaderState`.

`AbstractRaftState` содержит единое правило перехода при большем терме и проверку голосования. `LeaderState` хранит
`nextIndex`, `matchIndex` и ожидания клиентов; `RaftLog` проверяет префиксы, заменяет конфликтующий хвост и хранит
commit index. Ответ репликации несёт исходный запрос и номер отправки, чтобы задержанные ответы не отменяли прогресс
пира.

`PeerClient` выполняет сетевые запросы на виртуальных потоках и возвращает результаты событиями. Контроллеры RPC и
записи возвращают `CompletableFuture`, не ожидая ответ в потоке HTTP. Контроллеры чтения используют один опубликованный
через volatile неизменяемый снимок. Election timer имеет эпоху: сброшенный или отменённый таймаут не запускает выборы.

Логи переходов и голосования — INFO; heartbeat и сетевые ошибки — DEBUG. Для подробностей:
`--logging.level.ru.nsu.raft=DEBUG`.

## Проверка отказа

1. По `/status` найдите лидера, добавьте команду и сравните `/log` всех узлов.
2. Остановите процесс лидера. Два оставшихся узла выберут нового; отправьте ему следующую команду.
3. Запустите остановленный узел с прежним профилем: он получит актуальный лог и станет фолловером.
4. Оставьте один узел из трёх: новые записи не получат подтверждения большинства.

Автоматические тесты проверяют голосование, split vote, устаревшие события, кластер из одного узла, больший терм во всех
типах RPC, фиксацию большинством, изоляцию лидера, восстановление конфликтующего хвоста, неизменяемость снимков, работу
event loop после исключения, эпохи таймеров и HTTP API.

## Границы реализации

Терм, голос и лог хранятся **в памяти**. Перезапуск стирает их: эта лабораторная реализация не обеспечивает гарантий
Raft при произвольных повторных падениях и перезапусках большинства узлов. Для таких гарантий требуется сохранение
`currentTerm`, `votedFor` и лога на устойчивый носитель до ответа RPC (§5.2). Возвращённый пустой узел может
восстановиться от работающего большинства, сохранившего лог.

Команды пока только сохраняются в логе. Применение к key-value, CAS и distributed lock (этапы 3 и 4) не реализованы. Их
можно добавить как применение зафиксированного префикса к машине состояний, сохранив текущий протокол репликации и
очередь событий.
