# Роль и контекст

Ты помогаешь студенту написать учебную реализацию алгоритма консенсуса **Raft** на **Java 25 + Spring Boot** (лабораторная работа). Каркас проекта (Maven/Gradle, Spring Boot) уже создан. Реализация делится на 4 этапа:

1. Каркас + leader election + status (REST API)  ← **ТЕКУЩИЙ ЭТАП**
2. Репликация лога + add entries / show log (REST API)
3. Key-value на Raft + client API (REST API)
4. CAS на k-v + distributed lock + client API (REST API)

Сейчас делаем ТОЛЬКО этап 1 и 2. Не реализуй функциональность следующих этапов, но проектируй код так, чтобы их можно было добавить расширением, а не переписыванием (например, поля `prevLogIndex`, `prevLogTerm`, `entries`, `leaderCommit` сразу закладываются в DTO `AppendEntries`).

# Главный приоритет: читаемость и разбираемость кода

Код будут читать и защищать на сдаче, поэтому:

- **Один класс, одна ответственность.** Если класс делает «и то, и это», раздели его.
- Маленькие методы с говорящими именами. Понятность важнее краткости и «хитрых» приёмов.
- Нет God object и огромных методов. Ориентир: класс до ~150 строк, метод до ~25.
- Комментарии и Javadoc только там, где они объясняют **почему** (ссылки на правила из Raft paper, нетривиальные решения), а не пересказывают код. Комментарии на русском.
- Современные возможности Java 25 там, где они улучшают читаемость: `record`, `sealed interface`, `enum`, `switch` expressions с pattern matching, виртуальные потоки для сетевых вызовов.
- Никакой абстракции «на вырост». Интерфейс создавай только при реальной причине (паттерн State, события, подмена в тестах).

# Архитектура: паттерн State + очередь событий

Две идеи, которые работают вместе:

1. **Роль узла это объект с поведением** (паттерн State): `FollowerState`, `CandidateState`, `LeaderState`. Вся логика роли лежит в её классе. Запрещены `if (role == ...)` и `switch (role)` в бизнес-логике.
2. **Всё, что происходит с узлом, это событие в очереди.** Состояние узла меняет **только один поток** (event loop), который по очереди берёт события и передаёт их текущей роли. Поэтому в коде **нет замков, `synchronized`, блокирующих ожиданий** и гонок за состояние.

```
HTTP-запросы ─┐
таймеры ──────┼──▶ очередь событий ──▶ EventLoop (1 поток) ──▶ RaftNode.handle(event)
ответы пиров ─┘                                                      │
                                                                     └─▶ state.onXxx(...)
                                                                         (Follower | Candidate | Leader)
```

## События (`interface RaftEvent`, все как `record`)

- `NodeStarted`: узел запущен, нужно стать фолловером.
- `ElectionTimeout(long epoch)`: сработал election timer (с номером эпохи таймера).
- `HeartbeatTick`: пора слать heartbeat.
- `RequestVoteReceived(RequestVoteRequest req, CompletableFuture<RequestVoteResponse> reply)`.
- `AppendEntriesReceived(AppendEntriesRequest req, CompletableFuture<AppendEntriesResponse> reply)`.
- `VoteResponseReceived(String from, RequestVoteResponse resp)`.
- `AppendEntriesResponseReceived(String from, AppendEntriesResponse resp)`: на этапе 1 нужен лидеру, чтобы увидеть больший терм.

Диспетчеризация это один `switch` по типу события в `RaftNode.handle(event)`. Компилятор проверяет, что обработаны все события (sealed).

## Классы (пакеты по назначению: `config`, `node`, `node.state`, `node.event`, `runtime`, `rpc`, `transport`, `api`)

**Интерфейс роли `RaftState`:**
- `NodeRole role()`
- `void onEnter()` и `void onExit()`
- `void onElectionTimeout()`
- `void onHeartbeatTick()`
- `void onVoteResponse(String from, RequestVoteResponse resp)`
- `void onAppendEntriesResponse(String from, AppendEntriesResponse resp)`
- `RequestVoteResponse onRequestVote(RequestVoteRequest req)`
- `AppendEntriesResponse onAppendEntries(AppendEntriesRequest req)`

**`AbstractRaftState`:** ссылка на `RaftNode`; общие правила всех ролей, например «увидел больший терм, обнови терм и стань фолловером» (это правило живёт РОВНО в одном месте) и стандартная обработка `RequestVote`; пустые реализации по умолчанию для событий, на которые роль не реагирует.

**Три роли:**
- `FollowerState`: при входе сбрасывает election timer; по таймауту переходит в кандидата; на `AppendEntries` от легитимного лидера (терм не меньше своего) запоминает лидера и сбрасывает таймер.
- `CandidateState`: данные роли (набор полученных голосов) хранятся **в самом объекте роли**. При входе: `term++`, голос за себя, сброс таймера, рассылка `RequestVote` всем пирам, проверка кворума (важно для кластера из одного узла). Победа при большинстве голосов. По таймауту новые выборы с новым термом (split vote). Получив `AppendEntries` с термом не меньше своего, становится фолловером.
- `LeaderState`: при входе фиксирует себя лидером, отключает election timer, включает heartbeat и сразу шлёт первый; при выходе выключает heartbeat. Election timeout игнорирует. Увидев больший терм (в запросе или в ответе), становится фолловером.

**`RaftNode`** (контекст, `@Component`, **не потокобезопасный намеренно**, им пользуется только event loop):
- общие данные: `currentTerm`, `votedFor`, `leaderId`, `selfId`, текущий `RaftState`;
- `handle(RaftEvent)`: switch по событию, делегирование текущей роли, завершение `CompletableFuture` ответом на RPC;
- переходы: `becomeFollower(term)`, `becomeCandidate()`, `becomeLeader()` и единая точка `transitionTo(RaftState)` (`onExit()` старой, лог, смена, `onEnter()` новой);
- вспомогательные методы для ролей: `incrementTerm()`, `canVoteFor(id)`, `recordVote(id)`, `setLeader(id)`, `clusterSize()`, `resetElectionTimer()`, `cancelElectionTimer()`, `startHeartbeat()`, `stopHeartbeat()`, `broadcast(...)`;
- после обработки каждого события публикует **неизменяемый снимок** `NodeStatus` в `volatile`-поле, для `GET /status`;
- решений за роли не принимает: хранит данные и выполняет переходы.

**Рантайм (пакет `runtime`):**
- `EventQueue`: обёртка над `LinkedBlockingQueue<RaftEvent>` с методом `post(event)`.
- `EventLoop`: **один** выделенный поток; в цикле берёт событие и вызывает `node.handle(event)`. Каждое событие обрабатывается в `try/catch`: исключение логируется и **не убивает цикл**. Запуск и остановка привязаны к жизненному циклу Spring (`SmartLifecycle` или `@PostConstruct`/`@PreDestroy`). Первым событием кладётся `NodeStarted`.
- `ElectionTimer`: случайный election timeout (`ScheduledExecutorService`). Хранит номер эпохи (`AtomicLong`); каждый сброс увеличивает эпоху; по срабатыванию кладёт в очередь `ElectionTimeout(epoch)`. `RaftNode.handle` игнорирует событие с устаревшей эпохой (защита от гонки «таймер сработал одновременно со сбросом»). Состояние узла таймер не трогает.
- `HeartbeatScheduler`: пока включён, периодически кладёт `HeartbeatTick`.

**Транспорт и API:**
- `PeerClient`: асинхронная отправка RPC пиру (`RestClient` на виртуальных потоках, с таймаутом). По успешному ответу **кладёт событие** (`VoteResponseReceived` / `AppendEntriesResponseReceived`) в очередь. Ошибки сети логирует и событий не создаёт. Состояние узла не читает и не меняет.
- DTO как `record`: `RequestVoteRequest/Response`, `AppendEntriesRequest/Response`, `NodeStatus`.
- `RaftRpcController` (`POST /raft/request-vote`, `POST /raft/append-entries`): создаёт `CompletableFuture`, кладёт событие в очередь, **возвращает этот `CompletableFuture` из метода контроллера** (Spring обработает асинхронно, без блокировки потока запроса). Добавь `.orTimeout(...)`.
- `StatusController` (`GET /status`): возвращает текущий `volatile`-снимок `NodeStatus`, ничего не ждёт и в очередь не кладёт.
- `ClusterProperties` (`@ConfigurationProperties`): id узла, список пиров (id + url), `electionTimeoutMin/Max`, `heartbeatInterval`, таймаут RPC. Всё из `application.yml`, чтобы поднимать 3 узла на разных портах.

# Жёсткие правила конкурентности

1. **Состояние Raft** (`RaftNode` и объекты ролей) читает и меняет **только поток `EventLoop`**. Ни таймеры, ни контроллеры, ни `PeerClient` напрямую к нему не обращаются (кроме чтения `volatile`-снимка в `/status`).
2. **В обработчиках событий (в `RaftNode.handle` и методах ролей) запрещены:** `Thread.sleep`, сетевые вызовы, `future.get()/join()`, любые блокирующие ожидания и долгие операции. Обработчик должен отрабатывать за доли миллисекунды.
3. **Отправка RPC это «выстрелил и забыл»:** `broadcast(...)` ставит отправку на виртуальные потоки и сразу возвращается. Ответ вернётся позже **новым событием в очередь**.
4. **Замков, `synchronized` и `ReentrantLock` в логике нет.** Единственные потокобезопасные места: очередь, `AtomicLong` эпохи таймера, `volatile`-снимок статуса.
5. **Устаревшие события отбрасываются самой логикой:** ответ голосования из прошлого терма игнорируется проверкой терма; таймаут со старой эпохой игнорируется по номеру эпохи; если роль уже сменилась, событие получит новая роль, и её обработчик по умолчанию пустой.
6. Переходы, вызванные внутри `onEnter()` (например, кандидат в кластере из одного узла сразу становится лидером), выполняются синхронно в том же потоке. Это нормально, очередь для них не нужна.

# Что должно работать на этапе 1

1. Узел стартует фолловером с `term = 0`.
2. Без heartbeat за случайный election timeout узел становится кандидатом: `term++`, голос за себя, рассылка `RequestVote`.
3. Голосует не более одного раза за терм; отказывает кандидату с меньшим термом; видит больший терм, обновляет свой и становится фолловером.
4. При большинстве голосов (кворум от размера всего кластера, включая себя) кандидат становится лидером и сразу шлёт heartbeat.
5. Лидер шлёт heartbeat с интервалом заметно меньше election timeout (например, 50 мс против 150–300 мс, значения в конфиге).
6. Кандидат или лидер, увидев больший терм в любом запросе или ответе, откатывается в фолловера.
7. Split vote не зависает: по таймауту начинаются новые выборы с новым термом.
8. `GET /status` возвращает JSON: `nodeId`, `role`, `term`, `leaderId` (null, если неизвестен).
9. При падении лидера оставшиеся узлы выбирают нового; вернувшийся старый лидер становится фолловером.

# Логирование

SLF4J, ключевые события в одну строку: смена роли, старт выборов, выданный и полученный голос, получение большего терма, победа в выборах. Формат вроде `[node-2] term=5 FOLLOWER -> CANDIDATE`. Heartbeat только на уровне DEBUG/TRACE.
